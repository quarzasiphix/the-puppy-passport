# Public contract drift scanner

Stage XR-18 (append-only queue). Stage IR-1's `docs/BACKEND_API_CONTRACT_SNAPSHOT.md` is a real,
correct point-in-time record of the Data API's exact grant/RPC surface, generated by querying the
live database directly — but a static markdown snapshot with no automation goes stale the moment
the next migration changes a grant or an RPC signature. Confirmed while building this: that
snapshot was dated against migration `20260101012200` (124 files); this repository is now at 135 —
real, demonstrated staleness, not a hypothetical concern.

## What was built

`scripts/contract-drift-check.mjs` (`npm run db:contract-check`) queries the live local database
for the exact same two contracts IR-1's snapshot documents — table `SELECT`/`INSERT`/`UPDATE`/
`DELETE` grants to `anon`/`authenticated`, and every RPC's real signature/return type/grantees —
and diffs them against a committed, machine-readable baseline
(`docs/backend-api-contract-baseline.json`), failing loudly (non-zero exit, one line per drift) on
any undocumented change. `--write` regenerates the baseline after a deliberate, reviewed contract
change — the same "generate + compare against a committed baseline" shape this session already
uses for the ESLint baseline (Stage IR-16).

Needs a live database (unlike `migration-preflight.mjs`, which is a pure static text scan) — grants
and signatures are a property of the actually-applied schema, not reliably derivable from
migration text alone without literally replaying every file's `create or replace`/`grant`/`revoke`
statements in order. Not wired into the fast no-Docker CI job for that reason; intended to run
manually or alongside `test:db` (which already needs a live database).

## Verified the detector actually detects drift, not just that it runs

Ran a real, live test rather than trusting the logic by inspection: `revoke select on
public.breeds from anon` against the running database, confirmed the scanner immediately reported
the exact real drift (`baseline {"anon":"SELECT",...} -> live {"anon":"",...}`) with a non-zero
exit code, then re-granted and confirmed the scanner returns to "no contract drift." The initial
baseline (70 tables, 36 RPCs) was generated fresh against the current, correct live schema after a
clean `supabase db reset`.

## Nullability drift — not covered by this scanner, documented honestly

This stage's own definition also names nullability drift. Not included in the automated check:
column nullability isn't exposed through the Data API grant/RPC surface this scanner queries (a
`NOT NULL` column is enforced at insert time regardless of what the API layer "knows"), and
`src/lib/supabase/types.ts` (Stage IR-5's real generated output) already reflects the live schema's
nullability exactly every time `npm run db:types` is re-run — a second, parallel nullability-only
tracker would duplicate what the generated types file already provides for free. Not built to
avoid that duplication.
