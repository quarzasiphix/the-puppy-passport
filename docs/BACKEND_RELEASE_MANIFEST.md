## Feature flags

- `VITE_FUNDRAISING_ENABLED` (`src/lib/fundraising-flag.ts`) — the only real feature flag in the
  codebase (confirmed by grep of every `import.meta.env.VITE_*` usage). Defaults to **off**
  (unset/anything other than the literal string `"true"`). Every fundraising route checks it and
  shows an honest "not yet available" state when off. The real compliance boundary (fundraising
  contributions are always `is_simulated = true`) is enforced at the RLS layer independent of this
  flag — see Stage AB/CJ-era audits in `docs/AUTONOMOUS_BACKEND_PROGRESS.md`.
- `markets.*_state` columns (`marketplace_state`, `adoption_state`, `transport_*_state`,
  `fundraising_state`) exist as an admin-facing readiness display but are not consumed by any
  gating logic anywhere in the app (documented, not a bug — see the "Feature flags/market
  configuration" stage in the progress log).

## External requirements — not configured, correctly deferred

- **No production Supabase project exists.** Everything in this manifest is against the local
  Supabase stack (`supabase start`/`supabase db reset`). See `docs/PRODUCTION_SETUP.md` for what
  standing up a real project would require (not yet approved/done).
- **No outbound email provider is integrated** (no SDK in `package.json`; `email` fields are only
  ever stored, never sent). See the "Outbox/email delivery reliability" finding in the progress
  log.
- **Social login (Google/Facebook OAuth)** is optional and unconfigured locally by default —
  `.env.example` documents the two variable pairs
  (`SUPABASE_AUTH_GOOGLE_CLIENT_ID`/`_SECRET`, `SUPABASE_AUTH_FACEBOOK_CLIENT_ID`/`_SECRET`) with
  no values; sign-in buttons show an honest "not configured" state until real OAuth app
  credentials are supplied by whoever owns that decision.
- **Required env vars for local dev** (names only, see `.env.example` — no values reproduced here):
  `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (both printed by `supabase start`/`supabase
  status`, not secret in a local-only context since they're the well-known local demo keys), plus
  the four optional OAuth variables above.
- **No `SUPABASE_SERVICE_ROLE_KEY`/`SUPABASE_SECRET_KEY` is ever read by any browser-reachable
  code path** — confirmed by grep; the browser client (`src/lib/supabase/browser.ts`) only ever
  constructs a client from the anon key. Server-side service-role usage (if any is added later)
  would need its own dedicated audit before a production push.

## What this manifest deliberately excludes

No API keys, JWT secrets, database URLs with credentials, or seeded/test personal data appear
anywhere above — every local Supabase key referenced by name here is the fixed, publicly-known
local demo default (identical in every fresh `supabase start`, never a real secret), and even
those are referenced by variable name only, not value.
