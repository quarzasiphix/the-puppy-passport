# Havenpaw — Current State Audit

Snapshot taken mid-build, after the local Supabase foundation + identity/org schema redesign +
core transport request flow, before auth/onboarding, operations tooling, or marketplace-on-real-
data work. See `docs/IMPLEMENTATION_PLAN.md` for the phase this corresponds to. **Historical —
superseded by `docs/MVP_TEST_REPORT.md` for "what actually works today."** One specific
correction: this file's "`vite build` could not verify" risk (section 6/7 below) was resolved on
2026-07-17 — native `node`/`npm` are on `PATH` in this sandbox after all (the file:// path-
resolution failure described below was specific to running the Windows node binary against a WSL
path, not a real limitation), and a real `npm run build` now completes cleanly and serves correctly
via `npx wrangler dev` (this project deploys as a Cloudflare Worker). See `docs/MVP_TEST_REPORT.md`
section 4 for the verification details. Treat every other claim in this file as historical too.

## 1. Framework & project structure

- **TanStack Start** (React 19, SSR via `@tanstack/react-start`/nitro), file-based routing via
  `@tanstack/react-router`, built through `@lovable.dev/vite-tanstack-config` (Vite 8 + a
  `rolldown`-based bundler). Package manager: npm (a `bun.lock` also exists from the original
  Lovable scaffold but isn't used in this session).
- **Routing**: 38 route files under `src/routes/`, file-based (`_public.*` = public layout,
  `dashboard.buyer.*` / `dashboard.breeder.*` = dashboards, `__root.tsx` = root shell +
  auth-hydrating `beforeLoad`). `src/routeTree.gen.ts` is generated by the router's Vite plugin —
  it only regenerates on `vite dev`/`vite build`; **this sandbox never ran a working dev/build
  session against these routes**, so it may be stale relative to the newest route files
  (`_public.signup.tsx`, `_public.adoptions.tsx`, etc.) until someone runs `npm run dev` for real.
- **Component structure**: shadcn/Radix primitives in `src/components/ui/*` (accordion through
  tooltip — the full shadcn set), shared marketplace cards in `src/components/cards.tsx`
  (`PuppyCard`/`LitterCard`/`BreederCard`), site chrome in `src/components/site-chrome.tsx`
  (`SiteHeader`/`SiteFooter`, now auth-aware with a mobile `Sheet` menu).
- **Styling**: Tailwind v4 via `@tailwindcss/vite`, custom design tokens in `src/styles.css`
  (CSS variables for the `font-display`/color palette), `tw-animate-css`. Not touched this
  session — the transport-first repositioning reused the existing visual language (`SectionHeader`,
  card grid patterns, `container-page` utility) rather than introducing new components.
- **Responsive behaviour**: existing pages already lean on Tailwind's responsive utility classes
  (`md:`/`lg:` grid columns throughout). The one gap that was actually fixed this session: the
  header's hamburger button was previously non-functional decoration — it now opens a real mobile
  nav `Sheet`.

## 2. What's connected to real data (Supabase)

- **Auth**: email/password sign up (`_public.signup.tsx`) and sign in (`_public.signin.tsx`) work
  end-to-end against local Supabase — `signUp`/`signIn`/`signOut` server functions
  (`src/lib/auth/actions.ts`), session hydration in `__root.tsx` `beforeLoad`
  (`src/lib/auth/session.ts`), client-reactive state (`src/hooks/use-auth.ts`).
  `dashboard.buyer.tsx` redirects to `/signin` when unauthenticated. Google/Facebook buttons exist
  and call `signInWithOAuth`, but show a "not configured" toast rather than faking success (no
  provider credentials are configured — intentional).
- **Breeder/foundation verification** (`_public.create-breeder.tsx`): reads/writes
  `user_verifications` for real — shows a live status card once a verification exists, otherwise a
  real submission form.
- **Homepage stats** (`_public.index.tsx`): the three hero numbers (verified orgs, available
  animals, planned litters) are real `count` queries against `organisations`/`animals`/`litters`,
  not hardcoded.
- **Transport request flow**: `_public.transport.request.tsx` (the 7-step form) writes a real
  `transport_requests` row + initial `transport_status_history` row
  (`src/lib/queries/transport.ts`). `_public.transport.tsx` reads the `public_transport_requests`
  view for its "community-visible requests" section. `dashboard.buyer.transport.tsx` and the
  transport section of `dashboard.buyer.index.tsx` list the signed-in user's real requests with
  status + next-action copy.

## 4. Reusable vs. duplicated

- **Reusable and worth building on**: `src/components/ui/*` (don't touch), `cards.tsx`'s visual
  shell (extract the JSX, swap the prop types when marketplace pages get connected),
  `site-chrome.tsx`'s nav/mobile-sheet pattern, `src/lib/queries/transport.ts` as the template for
  future query modules (`src/lib/queries/{organisations,animals,litters}.ts` don't exist yet),
  `src/components/ui/form.tsx` + zod + react-hook-form as the established form pattern
  (`_public.signup.tsx`, `_public.transport.request.tsx`).
- **Duplicated (low-priority cleanup, not blocking)**: a local `Card`/`SectionCard`/`Section`
  wrapper component is redefined per-file in `dashboard.buyer.index.tsx`,
  `_public.breeders.$slug.tsx`, `_public.puppies.$id.tsx`, `_public.create-breeder.tsx`, and
  `_public.transport.request.tsx` — five near-identical `<div className="rounded-2xl border ...">`
  wrappers. Worth consolidating into one `src/components/section-card.tsx` **once** the pages that
  use them stop churning (don't do it mid-refactor of any one of them).
- **Not duplicated but worth flagging**: `dashboard.breeder.index.tsx` exports `Card` and
  `StatusPill`, imported by four sibling breeder-dashboard files (`litters.$id`, `applications`,
  `transport`, and indirectly others) — this is a real shared-component pattern already, just
  scoped oddly (exported from a route file instead of a components file). Leave as-is until that
  whole area gets rewired to Supabase; moving it now would just create merge noise later.

## 5. Environment variables & external integrations

- `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` — required, read in
  `src/lib/supabase/{browser,server}.ts`, throw a clear error at client-construction time if
  missing (no silent fallback).
- `SUPABASE_AUTH_GOOGLE_CLIENT_ID`/`_SECRET`, `SUPABASE_AUTH_FACEBOOK_CLIENT_ID`/`_SECRET` —
  optional, referenced by `supabase/config.toml`'s `env(...)` interpolation for OAuth providers
  (both `enabled = false` until real credentials exist).
- No other external integrations exist yet — no payments, no maps, no email service, no AI
  provider. Everything currently in the repo is either local-Supabase-backed or explicitly mocked.

## 7. Risks that could block future transport functionality

1. **Migrations have never actually run.** Every table, enum, trigger, function and policy across
   24 migration files was hand-written and self-reviewed, not executed against a real Postgres
   instance. A first `supabase db reset` could surface: enum-value typos, a forgotten `alter table
   ... enable row level security`, a policy referencing a column that doesn't exist, or a
   `gen_random_uuid()`/`pgcrypto` extension issue. **This should be the very first thing verified**
   once Docker is available — before building anything else on top of this schema.
2. **`vite build` is unverified.** If the real build (on a machine without the WSL/Windows-node
   path quirk) surfaces a genuine error, every page built this session inherits it.
3. **`routeTree.gen.ts` may be stale.** New route files (`_public.signup.tsx`, `_public.adoptions
   .tsx`, `_public.foundations.tsx`, `_public.community.tsx`, `_public.planned-routes.tsx`) were
   added without ever running `vite dev`/`vite build` to regenerate the route tree. `npm run dev`
   should regenerate it automatically, but this hasn't been confirmed to work end-to-end in this
   session.
4. **The `animals` table's shape is transport-secondary.** It was designed for the marketplace
   (breeder puppy / adoption / private rehoming) with an inline snapshot approach on
   `transport_requests` for animals that aren't in that table. The queued "transport workflow
   refinement" task (dedicated reusable `animals` record + `transport_parties` table) will need to
   either extend this table or introduce a second one — worth deciding deliberately rather than
   accreting fields onto `animals` ad hoc (see `DOMAIN_MODEL.md`).
5. **No automated tests exist anywhere in the repo.** Every check this session was manual
   (`tsc`, `eslint`, self-review). The "MVP integration review" phase at the end of the current
   queue is the first point real test coverage gets discussed — worth pulling forward in small
   pieces (e.g. pricing-calculation tests, matching-engine tests) as those modules get built,
   rather than deferring all testing to the very end.
6. **The `npm install`-via-Windows-npm incident.** Already fixed (see `DECISIONS.md`), but it's a
   sharp edge specific to this sandbox that will recur if a future session runs `npm install`
   through the same path — flagged in `CLAUDE.md` and `DECISIONS.md` so it isn't repeated.

## 8. Recommended implementation order (near-term)

This matches `docs/IMPLEMENTATION_PLAN.md`'s "immediate next slice," but the audit adds one thing
in front of it:

0. **Verify the schema actually runs.** Get Docker available (locally or in a follow-up session)
   and run `npm run db:start && npm run db:reset`. Fix whatever surfaces. Nothing else in the
   queue should be treated as "done" until this passes, since every later phase builds on this
   schema.
1. Auth + onboarding foundation (password reset, session-expiry handling, purpose-driven
   onboarding, `docs/SOCIAL_AUTH_SETUP.md`).
2. Navigation + role-based dashboard shells (so later phases have somewhere real to attach UI,
   instead of every dashboard being a flat unguarded route).
3. Transport workflow refinement (`animals`, `transport_parties`, drafts) — decide the `animals`
   table question from risk #4 above before writing more migrations that touch it.
4. Everything after that, in the order already recorded in `docs/IMPLEMENTATION_PLAN.md`.

I have **not** made broad visual changes in the course of writing this audit, and the only code
edits this session outside the explicitly-requested schema/auth/homepage/nav/transport work were
the `types.ts` inference fix and the `zod`/lint fixes required to keep `tsc`/`eslint` clean —
i.e. exactly the "small blocking issues required to run the application" latitude this task
allowed, nothing broader.
